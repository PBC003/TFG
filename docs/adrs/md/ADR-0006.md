## Context
El sistema requiere un mecanismo robusto de autenticación para diferenciar los roles de los usuarios (asegurando que solo el profesorado pueda crear preguntas y el alumnado solo pueda responderlas). Además, este mecanismo debe proteger las rutas de la API y mantener la sesión del usuario activa de forma segura. Se busca una solución estándar, que se integre fácilmente con la interfaz de React y que mantenga la filosofía de no guardar "estados" en el servidor, para que sea totalmente compatible con la arquitectura dockerizada del proyecto.

### Alternatives considered
- Sesiones tradicionales en el servidor (Cookies de sesión): Es un enfoque viable, pero obliga al servidor a recordar quién está conectado guardando esa información en memoria o en una base de datos adicional (como Redis). Esto complica la infraestructura y contradice el principio de las APIs REST (que deben ser sin estado o stateless).
- JWT guardado en el LocalStorage del navegador: Es la solución más sencilla de programar, pero presenta una vulnerabilidad de seguridad crítica frente a ataques XSS (Cross-Site Scripting), donde un código malicioso inyectado en la página podría robar fácilmente el token del usuario.
- JWT con token de refresco en cookie httpOnly: Es el estándar moderno. Combina una buena usabilidad con un alto nivel de seguridad al ocultar los datos sensibles al código JavaScript del navegador.

## Decision
Se implementará un sistema de autenticación basado en JWT (JSON Web Tokens) utilizando una estrategia de doble token:

1.	Access Token: Un token de vida muy corta (unos pocos minutos) que el frontend utilizará para autorizar cada petición a la API.
2.	Refresh Token: Un token de larga duración que el servidor enviará empaquetado en una cookie configurada como httpOnly. Esta configuración impide que el token sea leído mediante JavaScript, protegiéndolo de robos.

En el frontend (React), el estado de la sesión (los datos del usuario y su rol) se mantendrá en una variable en memoria. Si el usuario recarga la página y la memoria se borra, el sistema utilizará la cookie segura para solicitar un nuevo Access Token de forma transparente.

## Consequences
Pros:
- Ofrece un excelente equilibrio entre la seguridad del sistema y una experiencia de uso fluida.
- Elimina el riesgo de almacenar credenciales o tokens sensibles en el almacenamiento local (localStorage) del navegador.
- Se integra de forma muy natural con la arquitectura de la API REST desarrollada en NestJS.

Contras / riesgos:
- Exige configurar meticulosamente las políticas de seguridad del navegador.
- Necesita rotación/invalidación razonable de refresh tokens (p. ej., al logout).

## Compliance
- Las contraseñas de los usuarios nunca se guardarán en texto plano; se aplicará un algoritmo de hash seguro (como Argon2 o bcrypt) antes de almacenarlas en MariaDB.
- Se desarrollarán específicos en la API.
- Las cookies se configurarán con el atributo httpOnly estricto.
- Se implementará una limitación de peticiones (rate limiting) en la ruta de inicio de sesión para mitigar ataques de fuerza bruta.
- Todo el flujo de la sesión se documentará en la memoria final del TFG y en el archivo README.md del repositorio.
