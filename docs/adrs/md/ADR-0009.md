# ADR-0009 - Internacionalización del frontend con react-i18next

**Proyecto:** TFG – Plataforma de cuestionarios para Cálculo  
**Fecha:** 2026-03-19  
**Estado:** Accepted

## Estado

## Contexto
Debido a la situación de la escuela donde se imparte la carrera en dos idiomas la aplicación debe poder ser utilizada por todos los alumnos matriculados en la misma.

## Alternativas consideradas
- Mantener solo español y posponer cualquier internacionalización. Reduce trabajo inmediato, pero aplaza una deuda que seguirá creciendo con cada nueva pantalla.
- Gestionar textos manualmente con constantes o duplicaciones por componente. Es simple al principio, pero escala mal y dificulta la trazabilidad de cambios.
- Adoptar una solución estándar de i18n integrada con React y recursos por idioma. Permite ordenar el crecimiento del frontend desde ahora.

## Decisión
Se adopta `react-i18next` como base de internacionalización del frontend.

Los textos visibles deben pasar a claves de traducción y resolverse mediante recursos específicos por idioma.

Se establecen al menos dos recursos iniciales: español (`es`) e inglés (`en`).

El selector visible de idioma se implementa como control segmentado `ES | EN`, sin uso de banderas.

Las nuevas páginas y revisiones funcionales deben incorporarse directamente al sistema de i18n y no mediante textos hardcodeados.

## Consecuencias
**Pros:**
- Evita duplicaciones desordenadas y hardcodes difíciles de localizar.
- Permite revisar coherencia lingüística desde una fase temprana del proyecto.
- Deja alineadas la interfaz visible y la documentación técnica con una decisión real de producto.

**Contras / riesgos:**
- Exige disciplina para no introducir textos nuevos fuera del sistema de claves.
- Añade un pequeño coste de mantenimiento de recursos y revisiones de traducción.

## Cumplimiento
Debe existir un selector de idioma visible y debe de hardcodearse el minimo texto posible.
