## Context
El sistema maneja dos tipos de información con necesidades diferentes:

- Datos transaccionales vinculados a usuarios (roles, intentos, respuestas, puntuaciones, estadísticas base) donde interesa consistencia, relaciones y consultas estructuradas.
- Un banco de preguntas con posible evolución del esquema (nuevos tipos de preguntas, campos opcionales, metadatos, versión), donde interesa flexibilidad.

El objetivo es equilibrar la robustez de los datos de los usuarios con la facilidad de evolución de las preguntas, sin bloquear el desarrollo.

### Alternatives considered
- Un único motor SQL (MariaDB o PostgreSQL): Simplificaría el mantenimiento y la operación del sistema al tener un solo motor , pero obligaría a diseñar tablas muy rígidas que complicarían la evolución del esquema para acomodar diferentes tipos de preguntas matemáticas.
- PostgreSQL + JSONB: Es una opción intermedia que permite guardar datos flexibles (tipo documento) dentro de una base de datos tradicional. Evitaría tener dos motores distintos, pero requiere la adopción de PostgreSQL.
- MongoDB para todo: Facilitaría enormemente guardar modelos flexibles como las preguntas , pero empeoraría la gestión de la consistencia relacional y dificultaría la analítica fiable de los intentos y resultados de los alumnos.

## Decision
Se aplicará un patrón de diseño de persistencia políglota, utilizando la herramienta más adecuada para cada caso.
Se utilizará MariaDB para todos los datos estructurados (usuarios, roles ymétricas base). Paralelamente, se utilizará MongoDB exclusivamente para gestionar el banco de preguntas y cuestionarios e intentos.
Para conectar ambas partes, la base de datos MariaDB guardará identificadores estables (como un questionId) que apuntarán a la pregunta correspondiente almacenada en MongoDB.

## Consequences
Pros:
- MariaDB aporta consistencia y un modelo relacional sólido para datos críticos.
- MongoDB aporta flexibilidad para tipos de preguntas y campos variables.

Contras / riesgos:
- Implica una mayor complejidad operativa, ya que obliga a configurar, monitorizar y hacer copias de seguridad de dos bases de datos distintas.
- Al estar en bases de datos separadas, no se pueden realizar consultas combinadas directas de forma nativa. Estas uniones de datos tendrán que resolverse mediante lógica en la capa de la aplicación.
- Existe un riesgo de inconsistencias si no se define y programa correctamente la estrategia de identificadores (IDs).

## Compliance
- Diseño de esquemas claros: se usarán tablas relacionales estrictas en MariaDB y colecciones flexibles de documentos en MongoDB.
- Definición rigurosa de identificadores estables en la lógica del servidor.
- Uso de Docker Compose para orquestar y levantar ambas bases de datos simultáneamente, configurando volúmenes persistentes para que los datos no se pierdan al apagar los contenedores.
