## Context
El proyecto se desarrolla por una única persona, pero se gestiona con un enfoque basado en Scrum y revisiones periódicas con los tutores. En cada reunión de sprint se espera poder mostrar un incremento estable del producto.

Para reducir el riesgo de inestabilidad (trabajo a medias, cambios sin validar o errores), se separa el trabajo en curso del estado “demostrable”. Además, se busca mantener trazabilidad con Issues y Pull Requests sin añadir complejidad innecesaria para un proyecto individual.

### Alternatives considered
- Trunk-based (feature branches → `main`): flujo simple y habitual, pero `main` cambia continuamente y puede quedar inestable para demos o revisiones si no se extrema la disciplina.
- Una sola rama (`main`): mínima sobrecarga, pero aumenta el riesgo de romper el producto y hace más difícil aislar trabajo incompleto.
- GitFlow completo (develop + release/hotfix branches): aporta control adicional, pero es excesivo para un proyecto individual y añade burocracia sin aportar valor proporcional.

## Decision
Se adopta una estrategia ligera basada en dos ramas principales:

- `main`: rama estable, preparada para demostración. Solo se actualiza al final de cada sprint.
- `develop`: rama de integración durante el sprint.

El trabajo diario se realizará en ramas cortas creadas desde `develop` (por issue), integradas mediante Pull Requests. Al cierre del sprint se hará un merge `develop` → `main` y se etiquetará la versión demostrable (por ejemplo, `sprint-1-demo`).

## Consequences
Pros:

- `main` se mantiene estable y lista para demo o revisión en cada reunión.
- Aísla el trabajo incompleto en ramas de feature y en `develop`.
- Mejora la trazabilidad (Issue → branch → PR → merge) incluso siendo un único autor.
- Permite etiquetar releases por sprint y volver atrás fácilmente si fuese necesario.

Contras / riesgos:

- Ligera sobrecarga operativa (más ramas y PRs).
- Riesgo de merge grande al final del sprint si no se integra con frecuencia en `develop`.
- Requiere disciplina para mantener ramas cortas y evitar divergencia.

## Compliance
- Configuración de ramas `main` y `develop` en GitHub.
- Protección de `main` para evitar pushes directos y forzar merges mediante PR.
- Convención de nombres: `feature/<issue-id>-<short-name>`, `fix/...`, `chore/...`.
- PRs vinculadas a issues (por ejemplo, `Fixes #123`).
- Merge `develop` → `main` al cierre de cada sprint y etiquetado de la demo (por ejemplo, `sprint-1-demo`).
- Gestión del trabajo mediante GitHub Project (Board, Table y Roadmap), labels y milestones por sprint.
