## Context

El proyecto necesita un servidor (backend) que gestione toda la lógica de la aplicación: el registro y acceso seguro de los usuarios, la creación de los cuestionarios de Cálculo, la evaluación de los intentos de los alumnos y el cálculo de estadísticas. Este servidor tiene el reto de comunicarse simultánea y coordinadamente con dos bases de datos distintas (MariaDB para los datos relacionales de usuarios y MongoDB para el banco de preguntas y fórmulas matemáticas).
Además, la forma en que el servidor se comunica con el frontend (la API) debe estar bien documentada para facilitar su revisión y evaluación. Por último, el sistema debe ser fácilmente empaquetable en contenedores (Docker) y permitir la ejecución de pruebas automáticas.

### Alternatives considered

- Express o Fastify: Son herramientas muy populares y ligeras, pero al ser tan flexibles, requieren que defina y mantenga toda la arquitectura del proyecto. A medida que el TFG crezca, esto podría derivar en un código desorganizado.
- .NET (ASP.NET Core): Es una opción muy robusta y estructurada, pero utiliza el lenguaje C#. Ha sido descartada porque obligaría a usar lenguajes diferentes en el frontend y el backend, perdiendo la ventaja de tener un proyecto unificado en TypeScript.
- Python (FastAPI): Es una herramienta excelente para el desarrollo rápido de APIs, pero nuevamente impide compartir el lenguaje con el frontend (TypeScript). Si usáramos lenguajes distintos, no podríamos reutilizar el código que define la estructura de los datos.

## Decision

El desarrollo del backend se realizará utilizando el marco de trabajo NestJS programado en TypeScript. Se construirá una API REST, que es un estándar de arquitectura que permite que el frontend (React) y el backend se comuniquen enviando y recibiendo datos a través de peticiones HTTP convencionales.

## Consequences

Pros:

- Permite utilizar TypeScript en todo el ecosistema del proyecto (frontend y backend).
- Facilita enormemente la validación de los datos que llegan desde el frontend mediante el uso de DTOs (Data Transfer Objects, que son objetos que definen estrictamente qué forma deben tener los datos al viajar por la red, asegurando que no se procesen peticiones mal formadas).

Contras / riesgos:

- Curva inicial si no se ha usado NestJS previamente.
- Riesgo de sobrediseño si se crean demasiadas capas sin necesidad.

## Compliance

- El código se dividirá en módulos lógicos bien definidos: Autenticación, Usuarios, Cuestionarios, Intentos/Resultados, y Banco de Preguntas.
- Uso de DTOs para validar automáticamente todas las peticiones y devolver mensajes de error consistentes.
- Se desarrollarán pruebas mínimas automatizadas (unitarias y de integración) para asegurar que las partes más críticas funcionan correctamente.
